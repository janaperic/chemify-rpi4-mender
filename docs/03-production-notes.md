The delivered configuration is a **development and validation** configuration. This document lists what
to change before production use, why, and how. Items marked *recommended* are good practice; the others
are required. The integration was validated with the configuration as delivered; the changes below have
**not** been validated as part of Workstream A.

Mender's general guidance for production builds:
[Mender: build for production](https://docs.mender.io/operating-system-updates-yocto-project/build-for-production).

## 1. Remove the development login

**Why:** `EXTRA_IMAGE_FEATURES += "allow-empty-password empty-root-password allow-root-login"` in
`kas/chemify-rpi4-mender.yml` lets anyone with access to the serial console (or, with SSH installed, the
network) log in as `root` without a password.

**How:** delete the `EXTRA_IMAGE_FEATURES` line from the `chemify` section of
`kas/chemify-rpi4-mender.yml`. Create user accounts and credentials with your usual method (for example
`extrausers` / `EXTRA_USERS_PARAMS` with hashed passwords, or SSH keys only). See
[Yocto Project: image features](https://docs.yoctoproject.org/5.0/ref-manual/features.html#image-features).

## 2. Mender Server or standalone mode

**Why:** the image contains the meta-mender demo defaults in `/etc/mender/mender.conf`:

```json
"ServerURL": "https://docker.mender.io",
"TenantToken": "dummy",
```

With network access, the client would try to connect to that address. Choose one mode:

- **Managed mode (Hosted Mender or another Mender Server):** build every image and Artifact with the
  optional kas file `kas/hosted-mender.yml`, which sets `MENDER_SERVER_URL` and takes
  `MENDER_TENANT_TOKEN` from the environment (pass it from your CI secrets; never commit it). The
  complete procedure is in the [integration guide, section 10](01-integration-guide.md#10-connecting-the-device-to-hosted-mender).
  See also [Mender: build for production](https://docs.mender.io/operating-system-updates-yocto-project/build-for-production).

- **Standalone mode (updates only through `mender-update install`):** the `mender-updated` daemon must
  not run ([Mender: standalone deployment](https://docs.mender.io/artifact-creation/standalone-deployment)).
  During validation it was stopped manually after each boot (`systemctl stop mender-updated`). For
  production, disable it in the image, so that it stays disabled in both root filesystems after updates.
  Note that a mask created with `systemctl mask` on a running device only affects the current root
  filesystem.

## 3. Signing keys (R.1.4)

**Why:** the delivered verification key
`meta-chemify-rpi4/recipes-mender/mender/files/artifact-verify-key.pem` is a **temporary development key**
generated by Northern.tech for validation. Its private key is not handed over, so you cannot sign Artifacts
for devices that contain this key, and only you should hold the key that your devices trust. The first
steps are described in the integration guide, section 9.2. For production, also consider the following.

**How:**

1. Generate your key pair in a controlled environment (ideally an HSM or a dedicated signing
   service), with the commands from [Mender: sign and verify](https://docs.mender.io/artifact-creation/sign-and-verify)
   (RSA of at least 3072 bits, or ECDSA P-256).
2. Replace `artifact-verify-key.pem` in `meta-chemify-rpi4` with your public key. Never put a private key
   into the repository or the build system.
3. Sign every Artifact in your release process with `mender-artifact sign` (integration guide, section 9.2).
4. Plan key rotation. The client option `ArtifactVerifyKeys` accepts several public keys, which allows a
   transition from one key to the next.
5. Devices accept only Artifacts signed with a key they contain. When you change keys later, deploy the
   new public key with an update that is still signed with the old key **before** you retire the old key.

## 4. Time synchronisation

**Why:** the Raspberry Pi 4 has no battery-backed real-time clock. Without network time, the clock starts
at 1970-01-01 on every boot (observed during validation). TLS certificate validation, and therefore any
connection to a Mender Server, needs a correct clock.

**How:** `systemd-timesyncd` is enabled in the image and sets the clock once the device has network
access to an NTP server. Make sure the device can reach your NTP servers. For devices that must have the
correct time without network, add an RTC module. meta-mender provides the recipe `mender-wait-for-timesync`
to delay the Mender client until the time is synchronised.

## 5. Storage sizing (SoW: 7 GB available)

**Why:** partition sizes cannot be changed by an update, and since version 0.2 the data partition no longer
grows to the end of the card (integration guide, section 1.1). The delivered configuration sets:

| Partition | Size | Setting |
|---|---|---|
| Reserved (partition table, U-Boot environment) | 24 MiB | meta-mender default |
| Boot | 100 MiB | `MENDER_BOOT_PART_SIZE_MB` (base configuration) |
| Rootfs A and rootfs B | 2048 MiB each | calculated from `MENDER_STORAGE_TOTAL_SIZE_MB = "6288"` |
| Data | 2048 MiB, fixed | `MENDER_DATA_PART_SIZE_MB = "2048"` |
| Secrets | 1 MiB (in an 8 MiB aligned slot) | `MENDER_EXTRA_PARTS_SIZES_MB[secrets] = "1"` |
| **Image total** | **6296 MiB (6.6 GB)** | fits the 7 GB of the target |

`core-image-minimal` uses only a small part of the 2048 MiB rootfs partitions. Your product image must fit
into **one** rootfs partition, with headroom for future versions.

**How:** decide the rootfs size from your expected image size plus headroom, and the data size from your
application's needs. Then set `MENDER_DATA_PART_SIZE_MB` and `MENDER_STORAGE_TOTAL_SIZE_MB`; meta-mender
gives each rootfs (total − 104 − data − 8 − 32) / 2 MiB, rounded down to 8 MiB. The image is 8 MiB larger
than `MENDER_STORAGE_TOTAL_SIZE_MB` because of the extended partition, and must not exceed the
**smallest** storage you will ship. Larger rootfs partitions also mean that each update writes more data.
See [Mender: partition configuration](https://docs.mender.io/operating-system-updates-yocto-project/board-integration/partition-configuration).
Verify the result with `fdisk -l` on the `.sdimg` and on a device with the smallest supported card.

## 6. SD card wear and reliability (recommended)

- Use industrial-grade SD cards (pSLC or with wear levelling and power-loss protection) for products.
- Each rootfs update writes the inactive rootfs partition. `mender-flash` skips blocks that are unchanged
  (during validation, 1.82 GB of 2.15 GB were written for a first update, 12.6 MB for a repeated
  update of the same version), but plan for one partition write per update.
- Keep frequent writes off the root filesystem. In this image `/var/log` is already in RAM
  (`/var/log -> volatile/log`). Put persistent application data on `/data`, which is kept across updates.
- Consider a read-only root filesystem (`IMAGE_FEATURES += "read-only-rootfs"`); Mender supports it.
- Power loss during an update is handled by the A/B scheme (the active partition is not touched), but power
  loss during application writes to `/data` must be handled by the application.

## 7. Boot partition, firmware and device tree

**Why:** a rootfs update replaces the kernel (`/boot/Image` in the root filesystem), but **not** the boot
partition. The device tree used by the kernel is loaded by the Raspberry Pi firmware from the boot
partition, together with the overlays configured in `config.txt` (integration guide, section 8.1).
Changes to the firmware, `config.txt`, overlays or device tree are therefore not delivered by a rootfs
update. A future kernel update that requires a newer device tree or firmware needs a separate plan.

**How:** keep kernel, device tree and firmware versions compatible within a product generation. If boot
partition updates are needed, see the Mender Hub notes for this board:
[Raspberry Pi 4 Model B: Yocto 5.0 Scarthgap and later](https://hub.mender.io/t/raspberry-pi-4-model-b-yocto-5-0-scarthgap-and-later/7024).

## 8. `mender-prepopulate-inactive-partition` (optional)

**Why it is enabled:** it writes the root filesystem into both rootfs A and rootfs B of the `.sdimg`.
This is needed for the bootloader checks of the integration checklist and gives every new device a second
bootable root filesystem from the start.

**Production:** optional. Without it, rootfs B is empty until the first update, and the `.sdimg` is
slightly faster to write. Both variants work for updates.

## 9. Remove the `pseudo` backport (recommended)

**Why:** `meta-chemify-rpi4/recipes-devtools/pseudo/` exists only to make yocto-5.0.15 build on current
Ubuntu 24.04 hosts (integration guide, section 3.4.2).

**How:** when you move `openembedded-core`, `bitbake` and `meta-yocto` to yocto-5.0.21 or later (newer
Scarthgap point releases also contain security fixes), delete `recipes-devtools/pseudo/` from
`meta-chemify-rpi4`, rebuild, and repeat the validation.

## 10. Distribution, versions and LTS (recommended)

- **Distribution:** the build uses Poky, the Yocto Project *reference* distribution. Products normally
  define their own distribution configuration (security flags, package selection, users).
- **Artifact names:** set `MENDER_ARTIFACT_NAME` for each release in your CI (for example from a version
  tag). The value must be unique per release.
- **Mender Client LTS:** the image uses Mender Client 6.1 (LTS). When Mender publishes a new LTS release,
  the previous one remains supported for at least 6 months
  ([Mender: supported releases](https://docs.mender.io/release-information/supported-releases)). Plan to
  update the meta-mender pin in `kas/chemify-rpi4-mender.yml` accordingly.
- **Reproducibility:** keep using the lock file `kas/chemify-rpi4-mender.lock.yml` and update it
  deliberately (`kas dump --lock --inplace kas/chemify-rpi4-mender.yml`).

## 11. Serial console and offline start-up (recommended)

- **Serial console:** the image enables the UART (`ENABLE_UART = "1"`) and a login prompt on `ttyS0`. For
  products, decide whether the console is needed. If it is kept for service, protect it with credentials
  (section 1).
- **Offline devices:** the Mender services are ordered after `network-online.target`. Without a network
  connection, they start only after `systemd-networkd-wait-online.service` has timed out (about 2 minutes,
  observed during validation). If your devices often start without network, adjust the wait-online
  configuration for your network setup.

## 12. Secrets partition and layout change (version 0.2)

**Why:** version 0.2 adds the raw 1 MiB partition `secrets` for your encrypted secrets storage (integration
guide, section 1.2). Because an MBR partition table holds only four primary partitions, the data and secrets
partitions are logical partitions inside an extended partition, which changes the partition numbers.

**How:**

- **Address the secrets partition as `/dev/mmcblk0p6`** (not p5), or, after your software has created its
  encrypted container, by the container's UUID (for example `/dev/disk/by-uuid/<LUKS UUID>`). The partition
  has no label: MBR has no partition names, and there is no filesystem on it.
- **The data partition is now `/dev/mmcblk0p5`** (was p4) and has a fixed size of 2048 MiB. It is still
  mounted at `/data`; software that uses `/data` needs no change. Anything that refers to
  `/dev/mmcblk0p4` must be changed: p4 is now the extended partition and cannot be used directly.
- **Rootfs A/B remain `/dev/mmcblk0p2` and `/dev/mmcblk0p3`.**
- **Re-write devices that have the version 0.1 layout** with the version 0.2 `.sdimg`. A Mender update only
  replaces a root filesystem; it cannot change the partition table or create partitions. Data on `/data`
  of those devices is lost when the card is re-written; back it up first if needed. Do not deploy version
  0.2 Artifacts to devices with the 0.1 layout: the 0.2 root filesystem expects the data partition at p5.
- **Initialise the partition in your provisioning.** Its content after writing the `.sdimg` is undefined on
  re-used cards (only blocks that contain data are written). Rootfs updates, rollbacks and power cycles do
  not change it (validated, validation report section 8.4).
- **Size.** The default LUKS2 header (16 MiB) and LUKS1 (2 MiB) do not fit into 1 MiB. A LUKS2 container
  with a reduced header fits (integration guide, section 1.2). If you need more space, up to 8 MiB uses no
  additional space on the card (not validated).
- **Backups and wear.** The partition is part of the SD card; it is not protected against card failure or
  card cloning by itself. The security of the stored secrets depends on your encryption and key storage.
